# team-qa: 完了済みdirectionの独立QA

`team-qa <完了済みdirection> [対象環境] [対象ディレクトリ]` として明示的に起動する。対象環境の既定値を `local`、対象ディレクトリの既定値を現在のcheckoutとする。

実装工程から独立して完成物を受け入れる。QA資産は編集してよいが、製品コードを修正しない。自動commitもしない。

## 1. 入力と安全境界を確認する

1. direction全文、対象リポジトリの指示、変更差分、既存テスト、UI構成を読む。directionが完了済みでなければ `BLOCKED` とする。
2. 対象環境を確定する。明示がなければ必ず `local` を使う。
3. stagingなどの共有環境は、directionまたはユーザーが環境を明示し、かつプロジェクトの `prepare-qa-data` がその環境を許可するときだけ使う。
4. 本番環境へのデータ作成・削除、既存共有データの全消去、秘密値のskill・scenario・report・動画への記録、対象を限定できないcleanupを禁止する。

安全条件を満たせない場合は操作せず `BLOCKED` とする。認証情報を要求するときも値の保存先や報告本文へ秘密値を書かない。

## 2. 自動QAの適否を判定する

次のいずれかがあれば原則として実走する。

- 複数画面、権限・利用者差、状態遷移、またはデータ準備を含む
- 再発リスクがある、または変更箇所に接続する既存機能の回帰が懸念される
- 証跡や反復可能な回帰確認が必要である

UIに影響しない変更、文言・見た目の微修正、一度の人間確認で十分な変更、既存テストだけで受け入れられる変更は `SKIPPED` にしてよい。録画や環境起動のコストが人間確認を上回る場合も理由を明記して `SKIPPED` とする。

## 3. QA観点表を作る

directionの契約、検証設計、変更マップ、完了記載から、少なくとも次を候補化する。

| 観点 | 確認内容 |
| --- | --- |
| 主要正常系 | 利用者の主要ジョブと完了条件 |
| 空状態・境界値 | 初期状態、0件、上限付近、欠落値 |
| 権限・利用者差 | 許可・拒否、ロールや所有者の差 |
| 失敗・再試行 | 入力失敗、通信失敗、再送、復旧 |
| 接続機能の回帰 | 変更箇所の前後にある既存導線 |

各行を `今回実走`、`既存テストへ委ねる`、`人間確認へ残す` のいずれかへ割り当て、理由、必要状態、期待結果を記す。directionの完了条件を単に転記しない。変更リスクを覆う最小シナリオ集合に絞る。

## 4. データ準備方法を決める

各シナリオが要求する状態を列挙し、次の順で判定する。

1. 読み取り専用、固定fixture、既存の安全なテストデータだけで再現できるなら、その根拠を記録して続行する。`prepare-qa-data` は不要である。
2. データ作成や状態変更が必要なら、正本 `.agents/skills/prepare-qa-data/SKILL.md` と同期先 `.claude/skills/prepare-qa-data/SKILL.md` を探し、両方の存在と内容一致を確認する。
3. 両方ともない場合はSQL・API・seed手順を推測しない。片方だけ存在する、または内容が異なる場合もそのskillを実行しない。いずれも `BLOCKED` とし、先に `create-qa-data-skill` を明示呼び出しして生成・同期するよう案内する。
4. 両skillが一致していても対象環境が禁止、前提不足、実行コマンド未確認、安定識別子や限定cleanupが不明なら `BLOCKED` とする。

準備する場合は実行前状態を確認し、run単位の安定識別子で作成物を追跡し、準備後の検証を通す。固定fixtureならcleanup不要の理由を記録する。

## 5. scenario-kit資産を選ぶ

`scenario-kit` スキルを読み、`scenario-kit/scenarios/` を先に棚卸しする。選択順は次のとおり。

1. 既存シナリオをそのまま再利用する
2. 変更リスクを覆う最小範囲だけ局所拡張する
3. 足りない場合だけ新規作成する

QA資産として変更できるのは `scenario-kit/scenarios/` 以下だけとする。locatorや期待文言は製品ソースから確認し、推測しない。既存のproduction向けシナリオを書き換えず、必要ならlocal用を分ける。

## 6. 準備・実走・cleanupを行う

1. 必要なら `prepare-qa-data` の環境別手順でprepareし、検証して安定識別子を記録する。
2. 選んだ各シナリオを `npx scenario-kit qa <name>` で実行し、終了コードを保存する。
3. `report.json`、異常時スクリーンショット、`video.mp4` のパスを確認する。
4. 成功・失敗にかかわらず、`prepare-qa-data` が作成した対象だけにcleanupを試み、cleanup後の検証を行う。

scenario-kitの終了コードと `report.json` を優先し、動画だけを根拠に自動合否を決めない。cleanup失敗時はシナリオ自体の成否を併記し、最終状態を `BLOCKED` とする。

## 7. 判定する

- `PASS`: 計画したシナリオが完走し、検出対象の異常がなく、必要なデータcleanupも完了した。これは決定的な検査の合格を表し、文言・違和感・視覚品質の人間確認が残っていてもよい。その場合は動画の流し見を明示的に依頼する。
- `FAIL`: 製品挙動または既存シナリオに再現可能な問題があり、実装側へ証跡と再現手順を返せる。
- `BLOCKED`: 環境、認証、データ準備、安全性、またはcleanupの不足で実走・完了できない。
- `SKIPPED`: directionを読んだ結果UI実走の対象がなく、既存テストまたは人間の簡易確認が妥当である。

FAIL時も製品コード、migration、共有データを修正しない。期待値と実際値、再現手順、関連証跡、想定影響を実装側へ返す。修正は別の `team-impl` または通常実装へ渡し、修正後に同じシナリオで再実行する。

## 8. 結果を報告する

必ず次を含む短い報告を返す。

- 終了状態: `PASS | FAIL | BLOCKED | SKIPPED` と理由
- 今回実走した観点、既存テストへ委ねた観点、人間確認へ残した観点
- データ準備、安定識別子、検証、cleanupの結果（不要なら理由）
- 各scenario-kitシナリオ名、終了コード、`report.json`・スクリーンショット・動画の証跡パス
- `scenario-kit/scenarios/` 以下の変更ファイル一覧
- FAIL時の期待値・実際値・再現手順・想定影響、またはBLOCKEDの解除条件
- 動画の人間流し見など残る確認事項

`BLOCKED` または `SKIPPED` で実走していない場合も項目を省略せず、シナリオ名、終了コード、証跡パスをそれぞれ `なし（<実走しなかった理由>）` と記す。

QA資産のcommitは行わず、変更ファイルを報告してユーザー判断に委ねる。

入力にしたdirectionの実測フッターを、今回の終了状態（`PASS | FAIL n件 | BLOCKED | SKIPPED`）で更新する。すでに `QA` 欄があればその値を差し替え、無い旧形式のフッターには `逸脱:` の直前に `QA <終了状態>` を挿入する（今回入力にした1件だけの追記であり、他の過去directionへの遡及修正はしない）。「自動commitしない」原則は対象リポジトリのQA資産・製品コードに対するもので、このdirectionフッター更新だけは例外とする: directionの置き場がgit管理されていれば日本語メッセージでコミットする。
